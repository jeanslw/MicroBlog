# 常见问题

常见问题的排查与解答。部署步骤见[部署文档](部署文档.md)。

**Q: 页面样式错乱？**
确认 `static/lib/` 下 10 个 JS/CSS 文件及 `static/lib/fonts/` 字体完整存在（见 [README 前端静态资源](../README_ZH-CN.md#42-前端静态资源staticlib)清单）。

**Q: 数据库连接失败（MySQL）？**
- 确认 MySQL 服务已启动
- 确认环境变量 `BLOG_MYSQL_*` 配置正确
- 确认 `BLOG_DB_TYPE=mysql`
- 确认数据库 `flask_blog` 已创建

**Q: 数据库连接失败（SQLite）？**
- 确认 `BLOG_DB_TYPE=sqlite`
- 确认 `data/` 目录存在且可写
- 删除 `data/blog.db` 后重启可重置数据库

**Q: 如何切换数据库？**
修改 `BLOG_DB_TYPE` 环境变量（`mysql` 或 `sqlite`），代码自动适配，无需改动业务逻辑。

**Q: 管理员账号登录提示密码错误？**
密码通过 `generate_password_hash` 哈希存储，**明文密码无法登录**。注意 `BLOG_INIT_ADMIN_PWD` 仅在 admin 表为空（首次初始化）时生效一次，对已有账号改密码**无效**。重置密码请在 Python shell 中执行：
```python
from werkzeug.security import generate_password_hash
from app.models import Admin
from app.extensions import db

# 在 app context 中执行
admin = db.session.query(Admin).filter_by(username="admin").first()
admin.password = generate_password_hash("新密码")
db.session.commit()
```
若 admin 表为空（全新部署），也可直接浏览器访问 `/admin/setup` 通过引导页建号。

**Q: 经 nginx 反代后登录失败/登录后反复跳回登录页？**
最常见原因是生产模式默认 `SESSION_COOKIE_SECURE=true`，浏览器在**明文 HTTP** 下不会回传 Secure Cookie，导致登录态丢失。按以下顺序排查：
1. 内置 compose 的 nginx 仅提供 HTTP(80)，确认 `.env.docker` 中 `BLOG_COOKIE_SECURE=false` 后重建 web；配置 HTTPS(443) 后再置回 `true`
2. 确认反代转发了 `Host` 与 `X-Forwarded-*` 头，并设置 `BLOG_PROXY_XFOR=1`、`BLOG_PROXY_XPROTO=1`（compose 已内置默认值）
3. 多 worker / 多实例部署时，所有进程必须使用同一个 `BLOG_SECRET_KEY`，否则 session 无法互相验签
可参考 [nginx/nginx.conf](../nginx/nginx.conf) 的现成配置。

**Q: 请求返回 400，提示 "Invalid Host header" / "Host 'xxx' is not trusted."？**
应用启用了 Host 白名单防 Host 头注入。将访问用的域名/主机名（含端口，如 `blog.example.com`）加入环境变量 `BLOG_TRUSTED_HOSTS`（逗号分隔）后重启；留空则不校验。注意健康检查路径 `/healthz` 已豁免白名单，容器探针不受影响。

**Q: web 容器一直 unhealthy，或 `/healthz` 返回 503？**
`/healthz` 会执行 `SELECT 1` 探测数据库，503 说明应用进程正常但数据库不通：
- compose 部署：`docker compose logs web`、`docker compose logs db` 查看；MySQL 首启初始化期间应用会每 3 秒自动重连、最多等待 90 秒，超期仍失败请检查 `BLOG_MYSQL_*` 账号密码是否与 db 容器一致
- 直连 MySQL 部署：确认数据库已启动、账号有 `flask_blog` 的访问权限、`BLOG_DB_TYPE=mysql` 且必要字段齐全（缺失时应用拒绝启动而非静默回退）

**Q: 容器内上传图片/写 SQLite 报权限错误（Permission denied）？**
Linux 原生 Docker 下 bind mount 目录默认属主是 root，而容器以非 root 用户运行。镜像入口脚本 [docker-entrypoint.sh](../docker-entrypoint.sh) 已在启动时自动修正 `data/`、`static/banner`、`static/uploads`、`backups/` 的属主，使用最新镜像重建即可；自行定制镜像时请勿绕过该入口脚本。

**Q: 配置文件叫什么？改配置要注意什么？**
- **裸机 / 本地运行**：应用侧配置文件是 `app.env`（模板 `app.env.example`，`cp app.env.example app.env`），由 python-dotenv 在启动时加载；它在 `.gitignore` 中，不会入库
- **兼容**：仅当 `app.env` 不存在时才会回退读取旧版 `.env` 并打印迁移提示（`mv .env app.env`）；两个文件同时存在时以 `app.env` 为准
- **Docker**：容器内变量由 `docker-compose.yml` 注入，编排侧变量文件是 `.env.docker`（模板 `.env.docker.example`）；`app.env` 与 `.env` 都不会进镜像，改它们对容器无效
- 该文件仅在**进程启动时**读取一次，改完需重启服务（Docker: `docker compose --env-file .env.docker --profile full up -d`）
- 未安装 python-dotenv 时该文件不会生效，启动日志会给出对应告警

**Q: 改了代码怎么生效？**
- 裸机部署：重启服务（`gunicorn` / `python run.py`）
- Docker 部署：`docker compose build web && docker compose --env-file .env.docker --profile full up -d`
- 模板修改后需清理浏览器缓存

**Q: docker compose 启动报变量缺失/插值错误？**
当前 compose 已为密钥和密码提供测试默认值，`cp .env.docker.example .env.docker` 后**只需填写 `MYSQL_ROOT_PASSWORD` 与 `MYSQL_PASSWORD`** 两个密码即可启动（SQLite 模式 `docker compose up -d web` 连该文件都不需要）。若仍报错，注意：
- `docker compose` 会隐式读取项目根目录的 `.env`，但应用侧配置文件已改名为 `app.env`，**compose 不读取它**；只有残留的旧版 `.env`（如含 `BLOG_DB_TYPE=mysql`）才可能影响 SQLite 模式，删除该文件或用 `--env-file` 显式指定即可
- 编排的健康依赖条件需 Docker Compose **v2.20+**，旧版请升级（应用层另有 90 秒 MySQL 等待兜底）

**Q: 报 `microblog-env-check-1 ... service "env-check" didn't complete successfully: exit 1`？**
这是启动前预检守卫拦下的（正常时它会静默通过）。`up -d` 只打印这一行结论、**不打印守卫的说明**，先看日志定位：

```bash
docker compose --profile full logs env-check
```

- `[启动中止] ... 模板占位符`：`.env.docker` 是从模板复制来但密码没改，把两处 `请替换为强密码` 换成强密码（`openssl rand -base64 24`），或用 `docker compose --env-file .env.docker --profile full up -d` 时改好再启
- `[启动中止] ... 公开默认口令`：显式把 `MYSQL_ROOT_PASSWORD` / `MYSQL_PASSWORD` 设成了仓库中公开的测试口令，换成强密码即可
- `[启动中止] 缺少 MySQL/init.sql`：宿主机 `MySQL/init.sql` 丢失（bind mount 会把它变成空目录），从 git 恢复该文件
- 只有 `[安全警告]` 而没有 `[启动中止]`：无需处理。未创建 `.env.docker` 时会用 `db` 内置测试口令继续启动，仅限本机试用；公网部署前务必补上 `MYSQL_ROOT_PASSWORD`、`MYSQL_PASSWORD` 与 `BLOG_SECRET_KEY`

**Q: 首次启动很慢？**
MySQL 首次初始化要 30-60 秒，编排会等 `db` 容器 `healthy` 后再启动 `web`，且 web 启动时还会探测数据库可连接（每 3 秒、最多 90 秒）后才建表初始化，属正常。可用 `docker compose logs -f db`、`docker compose logs -f web` 观察进度。

**Q: Windows 上 gunicorn 启动失败？**
gunicorn 依赖 Unix `fork`，不支持 Windows。Windows 本地运行请改用已包含在 requirements.txt 的 waitress：
```powershell
waitress-serve --listen=127.0.0.1:5000 wsgi:application
```
Linux / WSL2 / Docker 内继续使用 gunicorn：`gunicorn -w 4 -b 127.0.0.1:5000 "app:create_app()"`。

**Q: 后台「数据库备份/恢复」失败，报 `returned non-zero exit status 2`？**
退出码 2 表示 mysql/mysqldump 客户端在**参数解析阶段**就拒绝了命令（典型输出 `unknown option '--xxx'`），此时它**根本没有连接数据库**——不是数据库损坏或数据问题。对备份而言，历史上最常见的就是客户端版本差异：`--skip-ssl` 只存在于 MariaDB / MySQL ≤8.0 客户端，**MySQL 8.4 的 `mysqldump` 已移除该选项**（因此备份与恢复都可能挂）。当前版本改为**行为驱动**：先用 `--skip-ssl` 真跑一次，客户端报「未知选项」就自动换 `--ssl-mode=DISABLED` 重试（未知选项在解析阶段即失败，不连库、不写库），两者都不支持则去掉该参数交给客户端默认行为，跑通的写法缓存复用；另外**不能用 `--version` 探测**来判定客户端认哪种写法——`mysql --skip-ssl --version` 会打印版本并以 0 退出（该客户端对 `--version` 提前返回、不再校验其余选项），而 `mysqldump --skip-ssl --version` 才会报错，同名参数在两个客户端里的校验时机不一致；失败时把客户端的原始 stderr 直接显示在页面上，不再只丢一个退出码。若页面显示的是别的文本，按文本排查：
- `Can't connect to MySQL server` / `Access denied`：地址、账号或 `BLOG_MYSQL_*` 配置不对
- `Unknown database 'flask_blog'`：目标库不存在，先建库或改用 SQLite
- `[WinError 2]` / `command not found`：宿主机没装客户端——本地裸机运行需安装 MySQL/MariaDB 客户端并把 `bin` 加入 PATH（容器镜像已内置，不受影响）

**Q: 把 Windows 上的备份恢复到 Linux 容器后，博客名变成了「My Blog My Blog」（或图片变破图）？**
备份**只含数据库**，不含 `static/uploads/` 下的上传文件（站点 Logo、头像、自定义背景、正文插图）。恢复后库里的 URL 还在，文件却不在新机器上，浏览器就把图片渲染成破图；导航栏 Logo 的 `alt` 恰好是站点名，破图会把这段 alt 文本画出来，紧接着又是页面上的站点名，看起来就像站点名被写了两遍。当前版本会在渲染前检查文件是否存在：Logo / 头像缺失时自动回落为内置图标与占位头像，不再出现破图与重复文字（库里的 URL 保持不动，把文件补回来后立即恢复显示）。完整迁移除备份文件外还需一并拷贝上传目录：

```bash
tar -czf uploads.tar.gz static/uploads           # 旧机器打包（Docker 部署在宿主机对应挂载目录执行）
tar -xzf uploads.tar.gz -C /path/to/MicroBlog    # 新机器解压到项目根目录
```
也可以在新机器后台「站点设置」/「关于我」页重新上传 Logo、头像与背景图；正文插图则需重新插入或按上面方式拷贝文件。

**Q: 语言切换不生效？**
确认 `translations/` 目录下有 `.mo` 编译文件。若修改了 `.po` 文件，需执行 `pybabel compile -d translations` 重新编译。
